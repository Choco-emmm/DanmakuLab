# 热点房间初步基线

当前状态：已有单/双进程压测入口；`-SplitProcesses` 分开两个真实 k6 进程并对齐计划起点。早期结果均为原调度；2026-10-25 后续新增可选 fair 房间队列与轮转，必须用 `-DispatchMode direct/fair` 核对所测模式，不能混淆历史基线与新实现。

## 1. 场景

默认建立 10 个普通房间，每房间 50 个观众、每秒 2 条输入；另建 1 个热点房间、500 个观众，合计 1000 连接。发送者也计入观众数，客户端轮流发送；所有观众正常读取，当前场景不注入慢连接。

连接全部加入之后，保持同一批成员依次运行四个阶段：

| 阶段 | 普通房间输入 | 热点输入尝试 |
| --- | --- | --- |
| normal-only | 每房间 2 条/秒 | 0 |
| hot-20-0 | 每房间 2 条/秒 | 20 条/秒 |
| hot-100-1 | 每房间 2 条/秒 | 100 条/秒 |
| hot-200-2 | 每房间 2 条/秒 | 200 条/秒 |

默认每阶段 30 秒，初步短轮可以指定 10 秒；`-PhaseSeconds 180` 才与 T4 设计的三分钟阶段长度一致。本脚本没有独立预热阶段，各阶段之间不清空令牌桶、不重建房间；阶段顺序、JIT、缓存、GC 和桶的初始突发额度都可能影响比较，后续正式对照需要重复与交叉验证。

服务端默认房间令牌桶为 50 条/秒、容量 50。热点尝试 100/200 条时预期出现 `room_rate_limit`，应完整记录接受与拒绝，不能声称实际接受了全部目标输入。脚本不修改限流，实际配置须结合归档的 application.yml 与 server-command.txt 阅读。

## 2. 启动和运行

在项目目录打包后启动缓冲模式；Windows 上重新打包前先停止占用 JAR 的旧服务：

```powershell
cd D:\coding\DanmakuLab
mvn -B -ntp verify
java -Xms128m -Xmx256m -jar target/danmaku-lab-0.1.0-SNAPSHOT.jar --server.port=8082 --lab.outbound.mode=buffered
```

另一个终端先运行 60 连接工具短轮，约 20 多秒：

```powershell
cd D:\coding\DanmakuLab
pwsh -NoProfile -File scripts/run/hotspot.ps1 -NormalRooms 2 -NormalConnections 5 -HotConnections 50 -PhaseSeconds 3 -LatencySampleEvery 1
```

确认工具运行、分母和清理后，可以运行 1000 连接、每阶段 10 秒的初步检查：

```powershell
pwsh -NoProfile -File scripts/run/hotspot.ps1 -PhaseSeconds 10
```

入口每约 10 秒提示已运行时间、每约 5 秒采样资源；k6 的分阶段消息和汇总保存在 k6-stderr.txt / k6-stdout.txt。每轮使用独立输出目录，已有目录拒绝覆盖。
默认入口 `-Mode buffered` 会核对服务实际模式；要测同步模式，须另启 direct 服务并明确传入 `-Mode direct -HttpUrl http://127.0.0.1:8081`。
房间调度默认 `-DispatchMode direct`，与输出模式是不同开关。新调度服务需显式用 `-DispatchMode fair`，例如 `-HttpUrl http://127.0.0.1:8083`；启动和顺序对照命令见 [房间调度](ROOM_DISPATCH.md)。fair 的队列拒绝或接受后丢弃会使当前正常读者场景失败，不会冒充允许的房间限流。

### 双进程对照

保持服务、连接数、输入速率和阶段长度不变，加一个开关：

```powershell
pwsh -NoProfile -File scripts/run/hotspot.ps1 -SplitProcesses -PhaseSeconds 10
```

入口会自动启动两个 k6 进程，无需手动打开两个终端：

- `normal`：只连接 10 个普通房间、500 条连接，每房间一直发送 2 条/秒。
- `hot`：只连接热点房间、500 条连接，依次尝试 0/20/100/200 条/秒。

默认先留 30 秒准备连接（`-StartDelaySeconds`，允许 10～120 秒），然后按同一个 Unix 毫秒起点计算四个阶段的计划时间。准备窗口不计入阶段输入时长，等待期间连接保持在线并发心跳。任一进程未在起点前加入完毕即失败。定时回调可能晚于阶段边界执行，此时先作一次有界补发（每房间最多 100 条），仍发不完本阶段计划则失败；下一阶段依然按共同绝对起点计算，不把迟到累积成新的计划边界。实际输入速率、启动滞后与发送滞后都会保留；小于 1000ms 的工具门槛仍较宽松，通过不表示实际收发严格同时或完全没有跨边界滞后。

输出目录中的 `normal/` 和 `hot/` 各保存 command、stdout、stderr、status 和 `k6-summary.json`。先看根目录 `comparison.json`（两边各房间的统计，不平均 P99），再看 `run-status.json`（两个 PID、进程退出、起点对齐、采集与回收），`counter-delta.json` 核对两边合计与服务端增量，`schedule.json` 记录共同起点，`samples.jsonl` 分别记录两个客户端进程与服务端的资源。

2026-10-26指标采集改为整轮复用一个HTTP `WebRequestSession`，在结束或异常时释放。原写法的60次GET本机实测新建60条TCP连接，复用后为1条；减少监控自身的短连接积累，不改变业务WebSocket。任何采样失败仍计入`collectorErrors`并令整轮失败，不补造采样或静默重试成“成功”。已有一次fair业务收齐但采集缺一帧的失败轮，见 [原始失败说明](results/2026-10-26/async-t4-fair-01/notes.md)；本机实测PowerShell 7.6.5。

独立进程消除了热点回调直接占用普通房间同一个 JS 事件循环的影响，但同机进程仍共享 CPU、内存和网络栈。该对照不是服务端耗时的精确分解，也不是独立机器实验。

不加 `-SplitProcesses` 继续使用原来的单进程负载。拆分前脚本的原始字节及 SHA256 说明保存在 [源码快照](results/2026-10-25/hotspot-combined-source/README.md)，历史结果的 manifest 保持不变。

## 3. 统计口径

- `sent`：业务发送调用成功返回的输入数；阈值同时要求等于计划数，并核对实际输入速率在目标的 ±5% 之内。
- `accepted / rejected`：逐输入去重的发送结果。热点只允许明确的房间限流拒绝；连接限流、其他拒绝或普通房间拒绝使本轮失败。
- `allInputDeliveryDemand`：实际发送输入数 × 本房间观众数；`acceptedDeliveryDemand`：已接受输入数 × 观众数。两个分母同时保留。
- `received / missingAccepted`：所有观众的真实唯一接收及已接受输入缺口。每个输入使用有界去重表，验证本轮/房间/实例标识、时间戳、正文、递增序号和观众间序号一致性。
- `missingResults`：已发送却没有收到接受/拒绝结果的输入数。不能通过缺失确认减少投递分母。
- 延迟从发送前的客户端时间戳到接收回调处理计算，默认每 10 个观众抽样一个；每个房间、阶段记录样本数和 P50/P95/P99，不平均不同房间的 P99。
- `maxSendLagMs`：输入相对计划时间的最大发送延后。当前工具门槛为小于 1000ms，超过即失败；该宽松门槛只是工具有效性下限，通过也不表示几十/几百毫秒的偏差可以忽略。
- 完整输入 JSON 为 256 UTF-8 字节，广播完整 JSON 的字节另行测量。每个进程使用一个 k6 VU；单进程模式协调全部房间，双进程模式只协调本角色的房间。各进程内部仍可能出现发送/接收回调调度滞后。
- 去重表按观众×计划消息计算，合计最多 64 MiB；这只是去重表容量，不代表 k6 进程总内存上限。

停止输入后有限等待 5 秒，再结算并关闭所有连接。入口核对服务端 input/accepted/rejected/expected/submitted 增量与客户端汇总，并检查连接、房间、预算与名额归零。成功只说明本轮工具/正确性检查通过，性能是否达标要另读实际结果。

## 4. 已观察到的限制与下一步

[千连接短轮报告](results/2026-10-24/hotspot-initial-report.md)记录到热点 100/s 阶段普通房间尾延迟抬升，同时 k6 的发送计划也明显延后。所有房间由同一个 VU 发收，因此暂不能把该现象完全归因于服务端的共享线程或房间调度。

2026-10-24时的状态：双进程入口已补齐，仍需比较单/双进程结果，并补重复实验、更长窗口和更细时序；当时正式T4及15/30分钟验收尚未完成。后续日期的结果另行归档。只有确认服务端争用证据后，才能把房间入口队列与公平调度的收益写成结论。

后续已实现可选 fair 机制，含房间入口预算和观众批次轮转；该实现提供明确资源边界，不将原压测器抖动当作它的优化收益，见 [机制与边界](ROOM_DISPATCH.md)。
同一新 JAR 的两种调度已完成顺序千连接短轮，各收齐 664500 次投递，未证明延迟优势，详见 [实现验证报告](results/2026-10-25/room-dispatch-report.md)。

[首轮拆分报告](results/2026-10-25/hotspot-split-report.md)：1000 条连接收到 664000/664000 次预期投递；热点 100/s 阶段普通房间 P99 为 12.02～25.01ms，对比此前单进程的 432.15～454ms。服务端未改动，结果支持先排查压测端影响；当前仅是短轮观察。
