# 从冒烟进入 T1 连接规模基线

本阶段回答：在相同输入速率下，100、500、1000 条连接的真实接收、延迟和资源占用如何变化？
这不是最大容量测试，也不包括慢消费者、每秒 20 条广播或 30 分钟稳态验收。

## 1. 固定实验条件

| 参数 | T1 默认值与口径 |
| --- | --- |
| 房间 | 每轮全新房间，全部连接在同一个房间 |
| 连接数 | 100 → 500 → 1000，包含轮流发送的客户端 |
| 建连 | 每 100ms 最多创建 20 条，等待全部 joined，最多等 60 秒 |
| 预热 | 60 秒，继续验证接收，延迟不混入测量窗口 |
| 正式测量 | 目标 180 秒；同时记录实际经过时间 |
| 输入 | 总共 5 条/秒，由房间内连接轮流发送 |
| 消息大小 | 完整输入 JSON 固定 256 字节；广播因附加元数据更大，另行测量 |
| 排空 | 输入结束后等 5 秒，再逐观众检查并关闭连接 |
| 接收完整率 | 所有连接的唯一接收数 /（固定连接数 × 900 条测量消息） |
| 延迟 | 抽样编号 0、10、20……的连接；报告原始毫秒值的 P50/P95/P99 与样本数 |
| 资源 | 每 5 秒采集客户端/服务端 CPU、工作集以及 JVM 堆、线程与业务指标 |

完整率公式要加括号理解：`实际唯一接收 / (连接数 × 900)`。每个观众还要单独收到全部 900 条。
100、500、1000 连接的测量期理论投递分别为 90,000、450,000、900,000 次；预热另计。
理论投递不是实测成绩，只有对应结果通过后才可以引用实际值。

## 2. 启动独立测试服务

终端 A，在项目目录中执行。重新打包前先停止占用目标 JAR 的旧进程。

```powershell
cd D:\coding\DanmakuLab
mvn -B -ntp verify
java -Xms128m -Xmx256m -jar target/danmaku-lab-0.1.0-SNAPSHOT.jar --server.port=8081
```

`-Xms128m` 是初始堆，`-Xmx256m` 是最大堆；Java 进程总内存还包括非堆、线程和本地资源，可能大于 256 MiB。
8081 用于本轮测试，避免演示页面产生额外输入干扰全局服务端计数。测试期间保留该终端运行。
本次比较各档使用同一服务进程、JAR、堆配置和消息模板，不能在中途切换广播实现。

## 3. 先验证入口，再逐档运行

终端 B 可以从任何目录调用绝对路径；以下使用先切换目录的方式，避免相对路径找不到脚本。

```powershell
cd D:\coding\DanmakuLab

# 短轮只验证工具，不能作为正式 3 分钟结果。
pwsh -NoProfile -File scripts/run/baseline.ps1 -Connections 10 -WarmupSeconds 2 -DurationSeconds 5 -HttpUrl http://127.0.0.1:8081

# 第一档，约四分钟加建连、排空和采集收尾。
pwsh -NoProfile -File scripts/run/baseline.ps1 -Connections 100 -HttpUrl http://127.0.0.1:8081
```

第一档通过后，再分别把 `-Connections 100` 改成 `500`、`1000`。每档失败时先看原始结果并定位原因，不能跳过失败。
如需自动顺序执行三档，并在任何一档失败时停止：

```powershell
foreach ($count in @(100, 500, 1000)) {
    pwsh -NoProfile -File scripts/run/baseline.ps1 -Connections $count -HttpUrl http://127.0.0.1:8081
    if ($LASTEXITCODE -ne 0) { throw "连接档位 $count 未通过，先检查结果再继续。" }
}
```

不要给本脚本添加 `--vus 1000`。它仍由一个 VU 的事件循环协调所有连接；连接数量由 `CONNECTIONS` 控制。
这也是测量边界：压测客户端仍可能先饱和，所以同时采集 k6 资源与实际输入速率。

## 4. 看哪些结果

每轮默认保存到 `docs/results/北京时间日期/t1-连接数-时间/`，拒绝覆盖旧目录。

- `k6-summary.json`：先看 `report`，包括真实接收数、缺失、重复、乱序、实际输入、延迟样本数及 P50/P95/P99。
- `server-delta.json`：运行前后业务计数之差是否匹配，连接和房间是否回到运行前状态。
- `resource-summary.json`：本轮采样最大工作集、堆、JVM 线程和相邻采样区间的最大 CPU 占比。
- `samples.jsonl`：一行一组资源和服务器指标，覆盖建连、预热、测量与排空；附采集时间，失败样本显式记录错误。
- `environment.json`、`config.json`、`commands.txt`、`source-sha256.json`：环境、JVM 命令、参数、命令和逐文件源码哈希。
- `run-status.json`、`k6-stdout.txt`、`k6-stderr.txt`、`notes.md`：退出码、过程日志和解释边界。

检查标准：所有连接加入；预热和测量消息逐人收全；缺失、重复、乱序、异常断连、拒绝和错误为 0；测量实际输入处于目标的 95%～105%；服务端计数匹配且清理完成；资源采集无错误。
顺序按服务端 roomSeq 递增且所有观众的消息/序号映射一致判断，不要求不同连接的客户端消息编号恰好按编号顺序取得房间锁。
连接/房间 gauge 等必需指标缺失会使校验失败；只有尚未创建的事件计数器允许按零处理，不能把未知的连接数当成清理到零。
T1 不设置延迟及格线，先保留真实基线。不能把超过候选延迟目标的结果删除或只保留最好的一轮。

资源数字也要解释口径：CPU 是相邻样本的进程 CPU 秒差除以实际间隔，再除以逻辑核数，按整机归一化。
例如 32 逻辑核机器上持续用满一个核约为 3.125%。低整机占比不能排除单个事件循环或一个线程先达到瓶颈。
所有资源最大值都是约 5 秒采样看到的值，不能称为绝对峰值；同机回环结果不能外推到公网或异机部署。

## 6. 当前线程模型

当前没有设置 `spring.threads.virtual.enabled`，也没有自行创建虚拟线程执行器。
Tomcat 使用 NIO 连接器与普通平台工作线程，配置工作线程最少 10、最多 100。
空闲连接不独占一个工作线程；消息到达后，容器安排工作线程调用 DanmakuHandler。
默认 direct 模式中，DirectBroadcaster 在该调用线程中取得房间锁并逐个同步发送，ClientConnection.writeNow 使用独立 writeLock 保证同连接不并发写。
因此一个慢观众会让该轮广播等在发送操作上，同时拖住房间锁；增加线程数量不会消除这个串行等待。

显式启用 buffered 后，房间锁内只按序投递连接邮箱，实际网络写交给共享的 8 个平台发送线程；另有 2 个关闭线程和 1 个周期检查线程。有限发送池仍可能被多个慢连接占满，详见 [输出模式说明](BOUNDED_OUTBOUND.md)。采集脚本将实际模式写入 config.json，并在 buffered 模式核对字节、条数与名额清理。

`jvm.threads.live` 是 JVM 存活线程总数，包含工作线程之外的线程；它既不是在线连接数，也不是正在执行广播的线程数。
堆、进程工作集与线程总数都是不同指标；需要结合实际连接与接收表现解释。
虚拟线程可作为以后单独的对照项，本轮不切换线程模型，避免同时改变多个实验条件。
