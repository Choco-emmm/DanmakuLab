# 学习问答：令牌桶、Java 语法与测试

记录日期：2026-10-23。本文整理阅读代码时提出的问题，说明当前实现；示例中的速率用于演算，不代表项目配置值。

## 一、限流原理与代码位置

### 1. 令牌桶是给单个用户的吗？

`TokenBucket` 只负责计算额度，本身不知道用户、连接或房间是谁。限制范围取决于谁持有这个桶，以及哪些请求共用它。

当前项目有两层限流：

| 持有位置 | 分配方式 | 限制范围 |
| --- | --- | --- |
| `ClientConnection.inputLimiter` | 每条 WebSocket 连接创建一个桶 | 这条连接发入服务端的弹幕 |
| `Room.inputLimiter` | 每个房间创建一个桶 | 房间内所有发送者的弹幕合计 |

当前没有账号系统，同一个人打开两个页面会建立两条连接，各自有独立的连接桶。以后如果要按用户限制，需要让同一 `userId` 的多个连接共用用户桶；这是后续设计，当前尚未实现。

一条弹幕先申请连接额度，再申请房间额度，两层都通过后才广播。当前策略是：房间拒绝时，已经消耗的连接额度不退回。

对应源码：

- [TokenBucket.java](../src/main/java/io/github/chocoemmm/danmakulab/core/TokenBucket.java)：余额计算与扣减。
- [ClientConnection.java](../src/main/java/io/github/chocoemmm/danmakulab/core/ClientConnection.java)：创建和持有连接桶。
- [Room.java](../src/main/java/io/github/chocoemmm/danmakulab/core/Room.java)：创建和持有房间桶。
- [DanmakuHandler.java](../src/main/java/io/github/chocoemmm/danmakulab/protocol/DanmakuHandler.java)：依次检查两个桶。

### 2. 额度怎样恢复？需要定时任务吗？

当前采用“按需补充”：没有请求时无需更新字段；下次调用 `tryAcquire()` 时，根据经过的时间算出应恢复的额度。每个桶不需要额外的线程或定时任务。

初始余额等于 `rate`，每次允许发送消耗 1 个令牌。余额不足 1 时立即返回 `false`，本次弹幕被拒绝，不在桶里排队，也不会自动重发；客户端之后重新发送时会再次检查。

令牌桶允许短时突发，不保证任意一秒窗口内严格最多发送 `rate` 条。

用户可见的行为：限流时服务端通过现有 WebSocket 连接返回 `send_result`，其中 `status` 为 `rejected`。连接桶拒绝的原因码为 `connection_rate_limit`，演示页显示“发送太快，请稍后重试。”；房间桶拒绝的原因码为 `room_rate_limit`，显示“房间消息过多，请稍后重试。”。本条弹幕不会广播，正常连接不因限流而主动关闭，也不会自动重试。当前页面在发送请求后就清空输入框，被拒绝后不会自动恢复原文；需要用户重新输入并发送。

### 3. 补充令牌的公式在哪个文件？是什么意思？

公式在 [TokenBucket.java](../src/main/java/io/github/chocoemmm/danmakulab/core/TokenBucket.java) 的 `tryAcquire()` 方法中：

```java
// 先按时间补充余额，再通过 Math.min 将余额限制在桶容量以内。
tokens = Math.min(rate, tokens + (now - lastRefill) / 1_000_000_000.0 * rate);
```

各个部分的含义：

| 表达式 | 含义与单位 |
| --- | --- |
| `tokens` | 上次计算后保留的令牌余额，可以带小数 |
| `now` | 本次读取的时间，单位为纳秒 |
| `lastRefill` | 上次计算补充量的时间，单位为纳秒 |
| `now - lastRefill` | 本次尚未结算的时间长度，单位为纳秒 |
| `/ 1_000_000_000.0` | 将纳秒转换为秒，并用浮点数保留不足一秒的时间 |
| `* rate` | 秒数乘每秒补充的令牌数，得到应恢复的令牌数 |
| `Math.min(rate, ...)` | 取较小值；当前实现将容量也设为 `rate`，防止无限积累 |

`1_000_000_000.0` 中的下划线只是方便阅读，它的数值就是十亿；小数点让这部分使用浮点运算。例如 500,000,000 纳秒可以换算为 0.5 秒。

这里是**除以** `1_000_000_000.0`，不是乘以：因为 1 秒等于十亿纳秒，所以“纳秒数 ÷ 十亿 = 秒数”。后面乘的是 `rate`，用经过的秒数计算应补充的令牌数。例如每秒恢复 1 个令牌，经过 500,000,000 纳秒，应恢复 `500_000_000 / 1_000_000_000.0 * 1 = 0.5` 个令牌。反过来，秒数乘十亿才是换算为纳秒。

可以把原公式拆开理解，以下是解释用写法，未修改业务实现：

```java
// 计算从上次结算到现在经过了多少秒。
double elapsedSeconds = (now - lastRefill) / 1_000_000_000.0;
// 经过的秒数乘每秒补充量，得到新增令牌数。
double addedTokens = elapsedSeconds * rate;
// 原余额加新增额度，但最终不能超过桶容量。
tokens = Math.min(rate, tokens + addedTokens);
```

这一步只负责补充，后面的 `tokens--` 才是扣掉本次发送需要的一个令牌。

### 4. 每秒恢复 1 个令牌时，怎样计算？

设 `rate = 1`，并假设在起点已经用完初始令牌，此时 `tokens = 0`、`lastRefill = 0`。下面的时间是为了演算设定的相对起点，不表示真实 `System.nanoTime()` 从 0 开始。

| 本次检查时刻 | 与上次检查相隔多久 | 补充计算 | 本次结果 |
| --- | --- | --- | --- |
| 经过 500ms | 0.5 秒 | `0 + 0.5 × 1 = 0.5` | 不足 1，拒绝；保留 0.5 |
| 经过 1000ms | 0.5 秒 | `0.5 + 0.5 × 1 = 1` | 允许；扣 1 后余额为 0 |
| 经过 1200ms | 0.2 秒 | `0 + 0.2 × 1 = 0.2` | 不足 1，拒绝；保留 0.2 |

第一行直接代入原表达式，就是：

```text
tokens + (now - lastRefill) / 1_000_000_000.0 * rate
= 0 + (500_000_000 - 0) / 1_000_000_000.0 * 1
= 0 + 0.5 * 1
= 0.5 个令牌
```

如果用完后直接等 3 秒才检查，内部表达式算出 `0 + 3 × 1 = 3`；但外层 `Math.min(1, 3)` 会将余额限制为 1。本次允许发送后再扣 1，余额回到 0。

### 5. `lastRefill` 是什么意思？怎样使用？

`lastRefill` 表示“上一次计算令牌补充量的时间”，用于标记哪些时间已经结算过。它不是上一次成功发送的时间，也不是上一次桶装满的时间。

它在三个地方起作用：

1. 构造器中执行 `lastRefill = clock.getAsLong()`，记录桶创建时的时间，作为首次计算的起点。
2. 每次申请时用 `now - lastRefill` 算出尚未结算的时间，按速率补充令牌。
3. 补充完执行 `lastRefill = now`，下一次只计算从本次到下一次之间的新时间。

即使本次拒绝，也要更新 `lastRefill`，因为小数额度已经加入 `tokens`。例如每秒恢复 1 个令牌，500ms 检查时已经补了 0.5 个；如果不更新时间，1000ms 再检查就会错误地再补 1 个，前 500ms 被重复计算。

余额与时间共同表示进度：`tokens` 记录已经结算的额度，`lastRefill` 记录结算到哪个时刻。正常业务使用 `System.nanoTime()`，这里只比较同一单调时钟的时间差，不把它作为日历日期。

`tryAcquire()` 的 `synchronized` 锁住当前桶实例，让读取时间、补充余额、更新时间、检查和扣减作为整体执行，防止多个线程同时拿走同一个令牌。不同桶各有自己的锁。

### 6. 为什么计算、检查和扣减需要放在同一个 `synchronized` 方法里？

假设桶里剩 1 个令牌，下面为理解并发而暂时忽略时间补充。如果没有锁，两个线程可能按这个顺序交错执行：

| 顺序 | 线程 A | 线程 B |
| --- | --- | --- |
| 1 | 检查 `tokens < 1`，发现余额为 1，可以通过 | |
| 2 | 尚未扣减，被系统切换出去 | 检查余额，看到仍为 1，也认为可以通过 |
| 3 | 扣减并返回 `true` | |
| 4 | | 继续扣减并返回 `true` |

余额检查发生在扣减之前，A 的检查结果不会自动阻止 B。即使只有一个令牌，两条消息也可能都被允许。`tokens--` 本身还包含读取、计算和写回，最终余额也可能出现其他错误；不能靠观察最终余额判断是否曾经重复放行。

对实例方法使用 `synchronized`，相当于进入时取得 `this` 对象的锁。另一个线程调用同一个桶的同步方法时，需要等待当前线程退出方法、释放锁之后，才能进入。

加锁后的流程是：A 进入方法，计算余额、检查并扣掉最后一个令牌，返回时释放锁；B 随后进入，按自己的当前时间重新补充和检查。如果此时还没恢复满 1 个令牌，B 就返回 `false`；如果期间已经恢复了足够额度，B 则可以正常通过。

这里“作为一个整体”是指针对使用同一对象锁的线程，不能在这段操作中间插入另一轮修改；方法内部仍然逐句执行。只锁 `tokens--` 不够，因为 A、B 仍可能在加锁前都通过余额检查。

锁属于具体桶对象，不是 `TokenBucket` 类的全局锁。不同连接桶可以分别执行；房间共享桶则需要争用该房间桶的锁。业务流量因此可以共享同一份房间额度。

需要区分两种等待：额度不足时返回 `false`，不会等待令牌恢复；但争用 `synchronized` 锁时，线程可能等待锁被释放。当前锁内只有时间读取和余额计算，没有网络发送或主动睡眠。

## 二、Java 语法与时间来源

### 7. `LongSupplier` 是什么？

`LongSupplier` 是 Java 的函数式接口，表示“不接收参数，返回一个 `long` 值”的操作，核心方法是 `long getAsLong()`。函数式接口可以理解为一份约定：这里需要一个能够提供 `long` 的方法。

在本项目中，`clock` 保存获取当前时间的方式，而不是固定的时间值：

```java
// 每次调用 getAsLong()，都向配置好的时间来源读取一次时间。
long now = clock.getAsLong();
```

正常业务通过 `System::nanoTime` 提供时间，测试通过可控的数值提供时间，因此令牌桶无需知道自己使用的是真实时钟还是模拟时钟。

### 8. `System::nanoTime` 和 `clock::get` 是什么意思？

`::` 是方法引用，表示把某个方法交给其他代码，以后需要时再调用。业务例子是“把读取时间的方法交给令牌桶，让它每次申请时自行读时间”。

- `System::nanoTime`：以后需要时间时，执行 `System.nanoTime()`。
- 测试里的 `clock::get`：以后需要时间时，执行这个 `AtomicLong` 对象的 `get()`，读取测试指定的数值。

把方法交进去时不会把返回值固定下来；真正执行读取发生在桶调用 `getAsLong()` 时。

## 三、测试方法与现有验证范围

### 9. 为什么测试使用模拟时钟？

为了快速、稳定地控制时间边界。每秒恢复 2 个令牌时，需要验证“499ms 不够、500ms 刚好够”。如果用 `Thread.sleep(499)`，线程可能因为调度延迟，在超过 500ms 后才继续，无法精确保证检查发生在 499ms。

模拟时钟让测试直接指定时间，无需真实等待 500ms 或 20 秒。只替换时间来源，补充、检查和扣减仍执行真实的 `TokenBucket` 代码。

### 10. 测试一般怎么写？项目现在测了什么？

基本步骤是“准备条件 → 执行操作 → 验证结果”。项目现有用例在 [TokenBucketTest.java](../src/test/java/io/github/chocoemmm/danmakulab/core/TokenBucketTest.java)。

下面是取自现有用例的核心流程，并补充阅读说明：

```java
// 准备：AtomicLong 是能安全读写 long 数值的对象，这里作为可修改的模拟时间。
// 初始值为 0，clock::get 让桶每次读取我们当前指定的纳秒数。
var clock = new AtomicLong();
var bucket = new TokenBucket(2, clock::get);

// 验证初始突发：容量为 2，因此前两次允许，第三次拒绝。
// assertThat(...).isTrue()/isFalse() 是断言，实际值不符合预期就判定测试失败。
assertThat(bucket.tryAcquire()).isTrue();
assertThat(bucket.tryAcquire()).isTrue();
assertThat(bucket.tryAcquire()).isFalse();

// 执行并验证时间边界：set 设置的是从模拟起点算起的时刻，不是增加这段时间。
// 到 499ms 只有 0.998 个令牌；到 500ms 累计达到 1 个。
clock.set(499_000_000);
assertThat(bucket.tryAcquire()).isFalse();
clock.set(500_000_000);
assertThat(bucket.tryAcquire()).isTrue();

// 验证容量上限：将时刻设为 20 秒，空闲后的余额仍最多为 2。
clock.set(20_000_000_000L);
assertThat(bucket.tryAcquire()).isTrue();
assertThat(bucket.tryAcquire()).isTrue();
assertThat(bucket.tryAcquire()).isFalse();
```

现有用例验证初始突发、时间恢复边界和容量上限。该用例没有验证多线程争抢，也不代表已经完成系统容量或性能验证。

在项目根目录执行现有令牌桶单元测试：

```powershell

mvn -B -ntp -Dtest=TokenBucketTest test
```
