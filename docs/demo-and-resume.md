# 五分钟演示与简历材料

适用当前发布候选和2026-10-28已复核结果。先练习单机演示，再选做Redis双节点；演示过程不重跑小时级压测。数据来源见[性能报告](performance-report.md)与[T3/T5正式记录](results/2026-10-28/longrun-repeat-02/notes.md)。

## 演示前准备

在PowerShell启动已归档JAR。参数显式开启local/fair/buffered；默认配置中的direct不会走完整两层队列。

```powershell
cd D:\coding\DanmakuLab
java -Xms128m -Xmx256m -jar target/danmaku-lab-release.jar --server.port=8080 --lab.cluster.mode=local --lab.dispatch.mode=fair --lab.outbound.mode=buffered --lab.outbound.workers=8
```

终端出现Started后，打开两个浏览器页面，地址都是`http://127.0.0.1:8080/`。这个HTML/CSS/JavaScript页面由同一Spring Boot服务提供，不需要额外前端开发服务器。若8080已有服务，可选空闲端口并同步修改下面的URL。

网页A昵称填A，网页B昵称填B，房间ID都填lobby，分别点击“连接并加入”。等待两个页面都确认加入后再开始。健康检查可在另一个终端执行：

```powershell
Invoke-RestMethod http://127.0.0.1:8080/actuator/health
```

## 0:00～1:00：展示同房间收发

A发送“你好”，A和B都应显示一次；B回复，两边也都收到。向面试官说明：发送者也在观众分母中，页面显示的是收到的广播，而服务器accepted只表示当前入口接受了请求。

可以这样说：“这是一个房间弹幕实验项目。我主要研究广播扇出、慢连接背压、队列预算和可验证的接收完整率。”

## 1:00～2:00：展示换房与隔离

把B的房间改为other，提交加入，等待确认。A在lobby再发一条，B不应收到；B在other发送，A也不应收到。B切回lobby后可继续双向发送，但离开期间消息不补发。

解释：每条连接只有一个活动房间；连接表记录真实Session，成员表记录连接所属房间。换房先检查新房间容量，成功后再移除旧成员，避免失败时丢失旧房间关系。

## 2:00～3:00：沿一条消息讲代码

打开[完整阅读导航](MESSAGE_PATH.md)，按以下顺序定位，不必现场背完源码：

```text
DanmakuHandler.send：校验完整帧/字段、连接与房间令牌桶
  → LocalBroadcastIngress.submit：选择本地路径
  → FairRoomDispatcher.submit：有界房间队列、序号与就绪房间轮转
  → DirectBroadcaster.deliver：把一次广播分发给成员快照
  → 各连接的OutboundMailbox：独立FIFO、条数/字节/全局预算
  → ClientConnection.writeAsync：容器异步发送
  → 完成回调与OutboundMailbox.finish：释放预算并激活下一条
```

重点解释两层队列：房间队列保存一次待扇出的输入，连接邮箱保存某个观众待发的消息。每连接最多一条在途，弹幕和控制回复走统一发送路径。8个线程是共享提交线程，不是整个JVM只有8线程，也不是每个观众一条线程。

## 3:00～4:00：展示接收证明与慢连接结果

打开[正式T3/T5报告](results/2026-10-28/longrun-repeat-02/notes.md)。先解释分母：

- T3：990名正常观众×20条/s×900秒＝17820000次/轮。三轮全收，抽样P99分别31/30/29ms。
- T5：1000人×20条/s×1800秒＝36000000次/轮。三轮全收，抽样P99分别36/39/37ms。

慢组是真正在recv前限速、缩小TCP接收缓冲，仍发心跳。写缓冲填满后会产生背压。输出邮箱负责有界积压和过期/过载策略，异步写避免把提交线程长期占在网络等待上。慢组被保护性断开后没有补建，所以本结果描述初始1%慢读条件，不能说全程10个慢观众或全场景零丢失。

观众解析弹幕后才计数、去重，并保留逐观众结果；accepted或服务端写完成都不能替代这一证据。P99按正常观众抽样，完整率检查全员，预热与测量分开。

需要现场演示自动检查时，在第二个终端运行3条消息的小冒烟即可。它是独立房间，不依赖网页上的手工消息：

```powershell
New-Item -ItemType Directory -Force load-results | Out-Null
k6 run --quiet -e MESSAGES=3 -e WS_URL=ws://127.0.0.1:8080/ws -e SUMMARY_PATH=load-results/demo-smoke.json scripts/load/smoke.js
```

期望joined=11、accepted=3、received=30/30，其余错误/重复/串房为0。重复演示会更新本地demo-smoke.json，不覆盖docs/results中的正式证据。

## 4:00～5:00：解释热点和扩展边界

打开[T4三对报告](results/2026-10-27/t4-workers-formal-01/notes.md)：六轮合计69267000次全收，热点合并抽样P99为6～7ms。每个普通房间P99单独保留；数据没有证明fair在所有阶段更快。曾遇到压测器发送滞后，因此把热点观众拆成5个进程并用全局编号、发送台账和逐观众位图复核，避免把客户端瓶颈当成服务器瓶颈。

Redis扩展用一句话说明：“每个JVM只持有自己的连接；Redis Pub/Sub传播广播事件，各节点再投本地房间队列和连接邮箱。来源节点也通过订阅接收，避免本地双发。”两个明确地址的操作见[双节点说明](CLUSTER.md)，不需要在这5分钟里临时部署。

结束后先在页面点击“断开连接”，再在服务终端按Ctrl+C。手工收发、隔离和讲解需要你亲自练习；文档写好不等于这次人工演示已验收。

## 简历可用版本

下列为项目描述草稿，使用前用自己的话讲清每条实现，并按实际参与范围调整。

**DanmakuLab｜实时弹幕广播与背压实验**  
技术：Java（源码release 21，实测JDK25）、Spring Boot、原生WebSocket、Redis Pub/Sub、Micrometer、JUnit、k6/Python。

- 实现房间加入/切换、连接生命周期、令牌桶限流与应用心跳；设计房间实例和消息序号，区分输入接受、写完成与客户端实际接收。
- 设计有界房间队列及逐连接输出邮箱，结合全局字节预算、轮转分发、每连接单在途异步写和过期/过载断连，处理慢观众背压及资源回收。
- 建立客户端真实接收、逐观众去重与服务端计数对账。在本机回环1000连接、初始1%慢读场景完成3轮15分钟验证，正常组每轮1782万次投递全收、抽样P99为29～31ms；另完成3轮30分钟稳态，每轮3600万次全收、P99为36～39ms。
- 实现可选Redis双节点广播和有界桥接，保留来源消息身份；覆盖订阅恢复与发布结果未知，定义按节点限流、不可靠补发及非全局严格顺序的语义边界。

版面只有两条时，保留“有界队列/异步写设计”与“带条件的实测数据”；Redis作为扩展能力写入技术栈或面试展开。不要把不同制品、不同负载的延迟相除，写成未经证实的性能提升倍数。

## 面试前自检

1. 为什么map中的Session不能直接放到Redis？能否区分本地连接所有权与跨节点事件？
2. 房间锁保护什么，网络等待为什么应在锁外？异步提交后何时才能释放在途预算？
3. 队列为什么同时限条数、字节和全局预算？队列满了，弹幕与控制消息分别怎么办？
4. accepted为什么可能晚于广播？为什么Redis PUBLISH确认仍不等于观众收到？unknown为何不自动重发？
5. 慢读与断网有何区别？慢组断开后不补建，对结论有什么限制？
6. 为什么压测器也会饱和？怎样用固定计划、全局分母和接收位图发现？
7. 哪些是当前实测，哪些仍未验证？能否说清本机、JAR、模式、人数、输入与抽样规则？

项目没有账号权限、普通弹幕历史、离线补发、集群全局限流/严格顺序，也没有最大容量或公网性能结论。面试时按这些边界解释设计取舍，并能指出原始结果的位置。
