# 多慢连接与异步输出

## 预检为什么失败

“混合”表示正常读者与慢读者一起在线；“预检”表示先缩短时长检查路径与配置，不是15分钟正式验收。2026-10-26以旧JAR、8发送线程重跑20连接（10正常、10慢读），测量20秒：正常收到1566/4000次，10正常连接全部失败，发送计划最大滞后约16ms，失败归档见 [修复前](results/2026-10-26/writer-fix-before-20/run-status.json)。

Python在预热后限制慢观众的原始socket.recv读取字节，目标1024B/s；正常读者持续读取，心跳仍发送。读得比广播流量慢，客户端TCP接收缓冲先填满，随后形成服务端发送背压。旧buffered虽有邮箱，实际写仍是同步session.sendMessage；慢写占满8线程后，正常邮箱也等不到发送机会，控制回复超过1秒而触发关闭。

TCP背压不能消除。需要避免的是应用把全部共享发送线程用于等待少数连接，而不是假装慢观众也能及时收齐。

## 当前改法

```text
广播/控制回复 → 每连接有界邮箱
                    ↓
8线程共享提交池 → native Async.sendText → 当前提交线程返回
                    ↓
           容器等待网络，完成或失败后回调
                    ↓
           只结算一次，释放在途预算
                    ↓
           本连接还有消息则再次激活
```

采用[容器异步发送API](https://tomcat.apache.org/tomcat-10.1-doc/websocketapi/jakarta/websocket/RemoteEndpoint.Async.html)，不调用Future.get/join等待。当前运行容器仍为Tomcat10.1.55，未因查询在线文档升级依赖。native异步端点设置5000ms发送超时；邮箱1秒年龄限制是尚未交给传输层的排队年龄，两者分开。

- 同连接只有一个Pending在途对象，弹幕、pong、joined、结果回复共用同一条路径，保证FIFO提交。
- inFlight在回调前仍占条数、UTF-8字节和全局预算；提交调用返回不代表完成。
- Pending.invoking处理“回调早于sendText返回”的情况：先记结果，等发起方法退出后再继续，避免递归或同时发第二条。
- 同步完成的快写每轮最多推进batch-size条；尚未完成的写立即让出线程，延迟回调后再激活。
- 回调重复、回调后又抛异常只能结算一次。失败先封住邮箱，注销时清理尚未发出的条目。
- 注销后还须等待物理关闭和在途写都结束才归还连接名额，防止断开/重连堆积旧写。强制停机取消关闭任务，也不能提前释放在途预算。
- 使用原生Jakarta会话；不支持时明确拒绝并归还准入名额，不暗中回退为阻塞网络写。

应用没有按连接创建线程，没有启用虚拟线程。容器仍使用自身I/O线程、网络缓冲与超时机制；异步不是无限资源，也不是可靠交付。

## 沿代码阅读

1. `ClientConnection.send`：buffered入邮箱；direct仍走同步基线。
2. `OutboundMailbox.offer`：检查预算、淘汰旧弹幕、激活一次任务。
3. `drain → ClientConnection.writeAsync`：取一条并保留预算，交给容器。
4. `finish`：成功计submitted，失败注销；回收预算，必要时恢复提交。
5. `ClientConnection.retireIfFinished`：关闭与写完成都收尾才释放名额。

`lab.outbound.writers.active`是正在执行提交代码的线程数；`lab.outbound.writes.inflight`是未结算写数。可以有10条在途写而没有提交线程被网络长期占住。这两个指标不能混为一谈。submitted也不等于客户端收到，仍需压测端逐连接去重计数。
