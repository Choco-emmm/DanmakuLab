# 提交与推送检查清单

适用范围：DanmakuLab 的代码、中文注释、学习文档、压测脚本和实验结果归档。
本文件是项目自己的人工检查模板，不是自动检查程序，也不替代外部技能所要求的配套清单。

## 使用方法

每次准备提交时，复制下面各项到本次提交说明或独立检查记录，再逐项执行。
`- [ ]` 表示未检查，`- [x]` 表示本轮已经检查通过；不适用的项目写明原因，不要直接勾选。
本模板中的勾选框始终保持未勾选，避免上一次通过被误认为本次也通过。
记录检查日期、目标分支、提交范围和验证输出位置；修改代码后重新执行受影响的检查。

## 1. 确认提交范围

- [ ] 使用 `git status --short` 查看修改、未跟踪文件和暂存内容，确认每个文件属于本次任务。
- [ ] 阅读 `git diff`；新增文件也单独阅读，因为未跟踪文件不会出现在普通 diff 中。
- [ ] 提交前阅读 `git diff --cached`，确认真正提交的内容与预期一致。
- [ ] 写清目标分支和提交说明；多个独立改动尽量分别提交，避免把无关修改混在一起。

本机若遇到 Git 的仓库所有权提示，可以对单次命令使用：

```powershell
git -c safe.directory=D:/coding/DanmakuLab status --short
git -c safe.directory=D:/coding/DanmakuLab diff
git -c safe.directory=D:/coding/DanmakuLab diff --cached
```

`safe.directory` 在这里仅作用于该次命令；它不代表代码已经通过审查。

## 2. 阅读代码与注释

- [ ] 新增或修改的代码符合根目录 AGENTS.md 的中文注释要求，说明职责、单位、步骤和失败后的行为。
- [ ] 并发改动说明共享状态、锁的对象与范围；同一连接的控制消息和弹幕仍经过统一发送入口。
- [ ] 连接加入、换房失败、发送失败和断开后，成员关系及资源回收符合协议约定。
- [ ] 修改队列或缓冲时，明确容量、字节预算、消息顺序、过期与过载处理，并检查资源释放。
- [ ] 注释区分当前实现、计划方案与实测结论；没有把未实现的优化写成现有功能。

## 3. 执行与改动相关的验证

- [ ] Java 或后端配置改变时执行 `mvn -B -ntp test`，检查测试总数、Failures 和 Errors，不能只看进程结束。
- [ ] 打包或启动方式改变时执行 `mvn -B -ntp verify` 并验证启动；Windows 上先停止占用目标 JAR 的进程。
- [ ] WebSocket 协议或收发脚本改变时运行小规模冒烟，确认 11 个 joined、接受 3 条、唯一接收 30 次，以及错误指标为 0。
- [ ] 修改 baseline 脚本时先跑短轮，核对逐观众完整率、实际输入速率、服务端计数差值和断开清理，再运行正式规模。
- [ ] 修改慢消费者脚本时检查 summary.json 的输入完成情况、拒绝与失败；Python 退出码为 0 不等于性能验收通过。
- [ ] 修改工具错误处理时，执行 `python -m unittest discover -s scripts/tests -v` 和 `pwsh -NoProfile -File scripts/tests/metrics.test.ps1`，验证初始化超时、失败发送计数与缺失指标处理。
- [ ] 修改子进程采集与失败收尾时，执行 `pwsh -NoProfile -File scripts/tests/process-evidence.test.ps1`，验证超时、非零退出与采样异常时仍有日志及状态，且子进程已结束。
- [ ] 前端行为改变时验证双页面收发、跨房间隔离、断开重连和文本安全展示；纯注释改动检查行为未变。
- [ ] 执行 `git diff --check` 检查差异中的空白错误；纯文档改动检查链接、命令和描述，无需重复完整压测。

冒烟示例，要求服务已在 8081 启动，在另一个终端执行：

```powershell
cd D:\coding\DanmakuLab
New-Item -ItemType Directory -Force load-results | Out-Null
k6 run --quiet -e MESSAGES=3 -e WS_URL=ws://127.0.0.1:8081/ws scripts/load/smoke.js
```

该命令会写入默认的本地 smoke-summary.json，正式归档需要独立目录；不要覆盖作为证据保留的历史文件。

## 4. 核对实验数据

- [ ] 本轮使用独立结果目录；失败、提前退出和成功轮均保留，报告如实区分。
- [ ] 保存实际运行命令、参数、工具/JVM 版本、网络路径和代码标识；有未提交代码时保留源码哈希。
- [ ] 明确连接数是否包含发送者；区分预热、正式测量和排空窗口，核对投递分母。
- [ ] 区分输入、接受、拒绝、服务端发送返回和客户端唯一接收；拒绝、重复、缺失、乱序及断连分别报告。
- [ ] 报告实际输入速率、延迟样本数和 P50/P95/P99；抽样规则、输入/广播 JSON 字节数分别说明。
- [ ] 明确资源采样间隔；采样最大值不称为绝对峰值，同机回环与单轮实验不外推公网或最大容量。
- [ ] 慢消费者结论有真实停读/限速和服务端证据；暂停页面显示不算 TCP 背压证据。
- [ ] 优化对照固定脚本版本、参数和环境；存在差异时明确列出，不能把条件变化当成优化收益。

具体口径见 [压测规范](BENCHMARK.md)、[T1 操作说明](BASELINE.md)和[慢消费者说明](SLOW_CONSUMER.md)。

## 5. 检查文件与文档

- [ ] 检查代码、配置、日志及结果，未包含密码、Token、Cookie、私钥等敏感信息；记录环境时也要检查启动参数。
- [ ] 确认 target/、load-results/、缓存、依赖目录和本地配置未误加入暂存区；正式证据放在 docs/results/。
- [ ] 注意 `.gitignore` 只影响未跟踪文件，已跟踪文件仍需要检查；结果中的本机路径和环境信息按实际分享范围审阅。
- [ ] README、协议、计划和结果报告与本次行为一致；链接指向存在的文件，未完成任务没有误标完成。
- [ ] 检查最终暂存清单 `git diff --cached --stat`，确认文件数量和体积合理，大体积原始数据使用索引及哈希记录位置。

## 6. 提交与推送后核对

- [ ] 提交成功后记录提交 SHA；使用 `git status --short` 确认是否还有未提交内容，并明确说明保留原因。
- [ ] 确认 origin 和目标分支正确，使用普通 push；远端有新提交时先检查分歧，不用强推解决。
- [ ] 推送后重新读取远端目标分支 SHA，与本地拟推送的提交核对，成功后才报告“已上传”。
- [ ] 最终说明提交内容、验证结果、GitHub 分支/链接及尚未解决的限制。

本清单记录检查步骤，不自动执行提交、推送或部署；实际操作仍按当次任务范围进行。
