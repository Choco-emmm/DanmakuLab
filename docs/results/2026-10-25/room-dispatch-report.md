# 房间入口与轮转实现验证

## 实现范围

新增可选 `lab.dispatch.mode=fair`，要求 `lab.outbound.mode=buffered`。一个共享平台线程轮转房间 FIFO；每轮最多完成 4 条输入或尝试 64 份观众投递，同房间前一条未遍历完，不开始后一条。默认仍是原调度路径。

每房间 64 条/64 KiB、全局 4096 条/4 MiB，预算包含正在分发的一条；状态名额受 `lab.max-rooms` 约束。检查成功才分配序号并计 accepted，容量拒绝不占序号。已接受输入仍可在首次分发前过期或因房间退休/停机被取消，不提供可靠交付。详细规则见 [ROOM_DISPATCH.md](../../ROOM_DISPATCH.md)。

## 自动验证

`mvn -B -ntp test`：**58 项通过，0 失败/错误/跳过**。包含原 direct / buffered 网络场景，以及新增 14 项调度单元测试、5 项拒绝协议测试和 7 项 fair 真实网络场景。日志和 XML 摘要保存在 [fair-verification](fair-verification/notes.md)，日志使用 `.txt` 扩展名避免被全局 `*.log` 忽略。之后用 `mvn -B -ntp package -DskipTests` 打包；未把跳过测试的打包命令称作另一次测试通过。

覆盖房间/全局条数、UTF-8 字节与调度状态名额；轮转轨迹、并发入队序号、跨批次快照；同名重建、过期缺口、异常后继续处理其他房间；停机时只释放等待条目、在途条目返回前仍占预算。协议测试核对五种稳定拒绝与关联 ID。真实 Tomcat 测试把十人广播分成多个批次，最终按客户端收件箱验证收到。

## 适用边界与后续

这是 Windows 同机回环的一对短轮，均无独立预热、未交替重复，两个服务进程同时在线但施压顺序执行；两边的 JIT、GC、缓存和主机其他负载不完全一致。新机制提供明确资源边界与有限工作轮转，不能据这对短轮宣称已改善性能、完全隔离热点、确定最大容量或完成 P0 长期验收。
