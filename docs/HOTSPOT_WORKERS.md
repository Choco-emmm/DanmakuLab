## 为什么不能直接启动五份旧脚本

旧热点脚本只识别自己的输入。新脚本的全部热点进程使用父进程传入的同一运行标识、
房间ID、共同起点；0/20/100/200每秒是整个热点房间的合计速率。
全局输入编号为k，发送责任由 `k % 工作进程数` 唯一确定，进程内再轮转发送连接。
1进程模拟500名热点观众；5进程各100人，普通房间始终另有一个旧客户端进程模拟500人。
输入JSON固定256个UTF-8字节，不因拆分而增加负载或观众总数。

所有进程必须在共同起点前加入。父进程不顺延起点；ThreadJob明确允许同时看守6个k6，
避免默认并发5把第六个客户端排到本轮结束。客户端另有自身的绝对起点校验。

## 接收证明

每个发送者保存实际发送时间、连接和accepted/rejected台账。每位观众保存覆盖全部输入
的位图，接收时可先记录其他进程的合法弹幕，晚于广播的accepted确认由离线审计器合并。
全局accepted集合与每位固定观众的位图逐项比对：少确认、少工作进程、少观众、
重复、非法来源和未知结果都不能缩小分母。五个进程各2人、各接受1条，共应收50份，
少1份就是49/50失败。热点应收始终为全局accepted数乘500。

来源、房间、正文、发送时间戳和序号同时校验。每10个全局观众编号抽1个延迟样本，
热点先合并0..120000毫秒直方图再求分位数；超界另计。普通房间保留每房间P99，
不平均P99。指标不放消息ID标签。终态后回调不会回写证据。

## 执行与失败规则

1. Python、Node、PowerShell检查与历史结果复核。
2. 60名观众、3秒阶段，1/5热点进程各一次。
3. 五热点进程，仅hot-0在20/s阶段暂停1.5秒，要求原发送滞后门槛失败，完整证据仍可审计。
4. 固定四轮：1、5、5、1热点进程，10×50普通观众、500热点观众，阶段各10秒，加入30秒、排空5秒。
5. `RunFormal`且全部前置条件满足：direct/fair、fair/direct、direct/fair，六轮阶段各180秒。

短轮四次都执行，正式轮失败立即停止后续正式轮，不自动重试、挑选成功成绩或放宽门槛。
五进程两次千连接短测必须同时通过：实际速率±5%、所有进程最大发送滞后<1000ms、
全员收齐、无异常拒绝/投递错误、服务端计数匹配、12项Gauge在有限10秒清理窗口归零。
单进程基线失败也保留；证据不完整不能支持结论。正式关闭额外短诊断和故障注入。

每次采样保留真实PID、CPU累计秒、工作集、线程和服务器指标。短测约1秒、正式约5秒。
报告客户端合计资源，输入/排空/关闭分段；观测差值不能直接叫服务端精确队列长度。
所有日志、退出码、超时、命令、源码/JAR哈希、发送台账、接收位图均有索引；
`k6-stderr.txt.gz`解压字节必须与原日志SHA-256一致。
