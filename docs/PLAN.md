# DanmakuLab 制作计划

制定日期：2026-10-22；时区：Asia/Shanghai。

## 1. 时间与完成标准

用户投入：每天 6 小时以上。安排约 54 小时主体工作，覆盖 10 月 22 日至 29 日；每天建议再预留约 1 小时处理环境、返工与学习。

“30 号之前完成”按 **2026-10-29 23:59 前核心交付完成**执行，10 月 30 日作为缓冲，不安排必须完成的新功能。若 22 日剩余时间不足，优先占用后续每日缓冲，削减扩展项，不压缩压测和收尾。

完成不等于搭好页面，必须同时满足：

- 两个浏览器可加入同一房间并实时收发；不同房间消息隔离。
- 消息、房间、连接和队列有明确上限；过载时有可观察的拒绝、丢弃或断连行为。
- 慢消费者不会造成应用层无限积压；有正常观众和慢观众同时在线的对照实验。
- 有热点房间与普通房间并存的隔离实验。
- 压测脚本、运行命令、环境配置、原始结果和汇总报告可复现。
- 能演示优化前后差异，并说明收益、代价和测试边界。
- README 可指导另一台符合环境要求的机器启动；准备好演示步骤和真实简历描述。

本轮只制作计划，不把文档中的设计当成已实现功能。

## 2. 项目定位

一句话：实现一个在突发广播和慢连接场景下仍能控制内存与延迟的实时弹幕系统，并用实验验证策略效果。

与现有项目的互补：Qgents 重点是长任务编排、写入冲突、失败恢复和交付一致性；DanmakuLab 重点是消息扇出、连接规模、排队、资源隔离和性能测量。

## 3. 范围分级

### P0：截止日前必须完成

1. Java 服务和简单原生网页：昵称、房间、弹幕发送、实时展示、连接状态。
2. WebSocket 协议：加入房间、弹幕、发送结果、错误与心跳；连接关闭后清理成员关系。
3. 输入约束：UTF-8 消息大小、字段长度、协议错误、单连接发送速率、房间输入速率和最大连接数。
4. 串行直接广播基线，以及可配置切换的优化广播模式。
5. 优化模式：房间入口有界队列、连接发送有界缓冲、统一发送入口、慢连接降级和断连。
6. 热点隔离：房间级准入/限流与有界批次调度，验证普通房间延迟受到的影响。
7. 指标：连接数、输入/拒绝/丢弃、发送缓冲、客户端接收量与延迟、JVM 和进程资源。
8. 功能与关键并发语义测试、压测脚本、基线/优化对照、演示与简历材料。
9. 浏览器断线后采用有上限的退避加随机抖动重连；明确重连不补发历史普通弹幕。

### P1：核心验收通过后推进

- 两个服务实例通过 Redis Pub/Sub 广播，展示跨节点房间收发、节点退出和重连。
- Prometheus/Grafana 仪表盘；P0 允许使用应用指标端点、结构化日志和结果图表完成观测。
- 5,000 至 10,000 连接的容量探索；若测到瓶颈，记录实际边界及归因。

P1 不作为虚构“分布式高并发能力”的依据；只有代码、场景和结果均存在时才能写入最终成果。

### 本轮排除

直播推流、支付礼物、商城、RAG/Agent、微服务拆分、Kubernetes、完整账号权限、弹幕历史检索、可靠消息补发、跨节点全局严格顺序、自研网络框架和复杂前端工程。

无需为普通弹幕实时路径引入 MySQL。后续若增加可靠消息或历史回放，再单独设计持久化语义。

## 4. 技术决策

| 项目 | 决策 | 原因与边界 |
| --- | --- | --- |
| Java | 源码以 Java 21 兼容为目标；初期使用已安装 JDK 25 验证 | 不为环境安装阻塞第一天；若最终只在 25 上验证，报告明确写 25，不声称验证了 21 |
| 后端 | Spring Boot + Spring MVC 原生 WebSocket | 直接控制房间成员、发送缓冲和降级策略；本轮不叠加 STOMP |
| 依赖版本 | 首日从官方发布信息确认兼容的稳定版本，固定到 pom.xml | 不使用动态版本或快照；记录实际 JVM、框架和工具版本 |
| WebSocket 容器 | 使用 Boot 默认 Servlet 容器，首版不更换 | 将时间集中在消息路径与实验 |
| 页面 | 原生 HTML/CSS/JavaScript，由服务提供静态资源 | 页面服务于演示，避免独立前端构建链 |
| 观测 | Actuator/Micrometer、结构化日志、压测客户端统计 | 服务端发送计数不能代替客户端接收计数 |
| 压测 | k6；Node 工具按需要补充真实慢连接模拟 | 不重复开发完整压测平台 |
| 部署 | 本机可启动，优先补一次 Linux 环境验证 | Docker 和外部服务器不作为 P0 启动前提 |
| 跨节点 | Redis Pub/Sub，仅 P1 | 普通弹幕允许断线丢失；不承诺持久化、可靠交付和全局严格顺序 |

## 6. 性能目标与承诺边界

候选稳态验收点：**单热点房间 1,000 条观众连接、20 条弹幕/秒、每条完整应用层 JSON 约 256 字节**。实际观众包含发送者时，按实际广播成员数计算理论投递量，约为 20,000 次/秒。

候选目标：稳定成员窗口内接收完整率 100%，客户端测得 P95 小于 200ms、P99 小于 500ms，连续运行 30 分钟无异常退出，应用队列始终在上限内。该目标不含被明确限流拒绝的输入；任何接收缺口、断连或主动丢弃都必须单独报告，不通过剔除断连用户美化结果。

这些是待验证目标，不能预写成成果。首轮结果不达标时，保留失败结果，定位瓶颈后复测；截止日前仍未达标，则交付真实容量边界和原因。

扩展负载：1,000 连接下逐级提高输入速率，以及固定输入速率下探索 5,000/10,000 连接。报告吞吐量、延迟、丢弃和资源变化曲线，不把连接成功等同于广播达标。
