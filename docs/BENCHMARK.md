# 压测设计与结果记录规范

状态：方法设计，尚无实测成绩。制定于 2026-10-22。

## 1. 先校验工具，再测容量

本机 k6 为 `v2.0.0-rc1`。首日用 10 个连接完成一次可核对消息数量的实验，确认 WebSocket API、统计窗口和结果输出正常；必要时切换稳定版本。

普通收发优先使用官方 `k6/websockets` API。真实慢连接需额外的网络限速手段；不能仅在 JavaScript 回调里延迟展示或休眠，然后声称模拟了 TCP 慢消费者。

基线和优化版本必须分别通过功能校验，性能对照以相同负载、消息内容、堆大小、线程配置和网络路径运行。版本或参数不同的地方必须写出。

## 2. 指标定义

| 指标 | 定义与采集位置 |
| --- | --- |
| 在线连接 | 服务端当前有效连接；压测端同时记录建立成功、失败、异常断开 |
| 输入速率 | 实际发送的弹幕请求/秒，不含心跳和加入消息 |
| 接受/拒绝 | 服务端通过准入的数量，以及按原因拒绝的数量 |
| 理论投递需求 | 测量窗口内逐条消息在分发时的目标成员数之和 |
| 服务端提交发送量 | 写入传输层或相应发送调用完成的计数；不能解释为观众实际收到 |
| 客户端接收量 | 客户端成功解析的业务弹幕，排除加入响应、确认、心跳和错误帧 |
| 接收完整率 | 固定成员窗口内实际唯一消息投递数 / 应有投递数；重复单独统计 |
| 端到端延迟 | 从发送者发出业务消息到接收者解析该消息；不等同于 ping 或连接耗时 |
| 应用队列 | 房间入口、连接待发和共享执行器的长度、字节数、最老年龄和峰值 |
| 资源 | JVM 堆、GC、进程 CPU/RSS、线程数、网络吞吐；尽可能观察 socket 内存 |

普通消息缺口按主动丢弃、过期、发送失败、断连影响、未知缺失区分。慢连接收到少量消息可能是预期降级，但必须同时报告其接收比例、丢弃数和断连数。

`accepted` 不是交付确认；服务器 `send` 成功也不是客户端交付确认。不得用它们替代接收完整率。

## 3. 计时和统计窗口

- 初版将发送者和接收者放在同一台压测机，以同一系统时钟的 `clientSentAt` 与接收时间计算延迟，不依赖服务端时钟。
- 记录毫秒级时钟分辨率及测试期间是否发生时间校正；明显异常的负延迟不能静默删除。
- 异机压测如需单向延迟，必须说明时钟同步和误差；也可使用同一客户端时钟的回环测量，但必须另行命名，不能混写。
- 建立连接并确认房间成员就绪后再启动测量；稳态计数阶段停止主动加入/退出。
- 输入停止后允许有限排空时间，再结算实际接收量；不能只测发送阶段并忽略尾部积压。
- 如果测量阶段发生异常断连，记录时间、数量及丢失影响；不从结果中删除这些连接以提高完整率。
- 同时报 P50/P95/P99、样本数、实际输入速率和错误数。不能把多个分组的 P95 取平均当成整体 P95。
- 正常观众与慢观众、普通房间与热点房间分别统计，不用总体平均数掩盖问题。
- 消息按 `messageId` 或运行标识与 `roomSeq` 检查缺口、重复和乱序；统计结构有界，不无限保存每个连接全部历史 ID。
- 若采用抽样测量延迟，明确抽样规则和样本量；完整率仍需可校验的计数与序号证据。

## 4. 测试矩阵

| 编号 | 场景 | 负载与时长 | 要回答的问题 |
| --- | --- | --- | --- |
| T0 | 功能与工具校验 | 10 连接，1 条/秒，1 分钟；另测跨房间 | 客户端是否真的收到，统计是否正确？ |
| T1 | 连接阶梯 | 100 → 500 → 1,000；各预热 1 分钟、测 3 分钟 | 建连和基础广播资源如何变化？ |
| T2 | 单房间吞吐阶梯 | 固定 1,000 连接，5 → 20 → 50 → 100 条/秒；各测 3 分钟 | 实际吞吐、延迟和拒绝从哪里恶化？每档显式配置房间限流 |
| T3 | 慢消费者 | 1,000 连接，1% 真正限速接收；先测 20 条/秒，必要时提高负载；15 分钟 | 是否形成传输层积压，正常用户受何影响，内存是否受控？ |
| T4 | 热点隔离 | 10 个普通房间各 50 人、各 2 条/秒；1 个热点房间 500 人，输入 20 → 100 → 200 条/秒；各测 3 分钟 | 热点过载是否影响普通房间？限流、丢弃和队列是否按设计生效？ |
| T5 | 稳态与清理 | 候选验收点 30 分钟，随后全部断开并等待清理 | 无异常退出；队列不越界；连接/成员/预算回收；内存趋势可解释 |
| T6 | 突发重连 | 先在 100 连接验证，再视资源提高；模拟部分断连与退避重连 | 准入、线程和资源是否失控？ |
| T7 | 容量探索，P1 | 5,000 → 10,000 连接，低速广播起步，再提高输入 | 空闲连接容量与广播容量有何差异？ |
| T8 | 双实例，P1 | 每节点先 100 连接；跨节点广播与关闭其中一个实例 | 是否重复投递，如何重连，哪些消息会丢失？ |

稳态候选目标：1,000 连接、20 条/秒、约 256 字节完整应用层 JSON，P95 < 200ms、P99 < 500ms，正常固定成员窗口完整率 100%。目标是否达到由实测决定。

T3 的“慢”需要有证据：限制 TCP 读取或接收链路速率，运行到容器/内核缓冲被实际压满，观察应用待发年龄、发送阻塞或降级。可采用本地 TCP 限速代理，或在可用 Linux 环境使用网络限速。增加客户端展示延迟不算完成该场景。

T4 的对照先固定相同限流参数比较调度改动，再单独改变限流参数；报告被拒绝的输入。不能通过少接收大量输入却不说明，制造“同吞吐下更快”的结论。

重复要求：关键基线/优化对照至少各 3 次；30 分钟稳态至少 1 次。每次独立记录，不挑最好一次代表全部结果；报告各次结果和汇总方式。

## 5. 控制变量与负载有效性

- 使用固定消息模板，记录完整 UTF-8 JSON 字节数；不是只记录弹幕正文字符数。
- 发送者数量应足以满足总输入速率，避免先被每连接限流挡住。
- 使用固定速率计划并记录实际达到的速率；广播压力变大后输入若明显下降，本轮不能声称达到了原定负载。
- 明确观众数是否包含发送者；理论投递数按实际成员计算。
- k6、慢连接代理和服务端同机时记录各自 CPU/内存；同机回环结果不等于真实公网容量。
- 检查压测器是否因 CPU、文件描述符、临时端口或结果写入速度先饱和。不能把压测器瓶颈当服务端容量。
- 不在每次投递路径打印完整日志；监控采集间隔和采样方式在对照中一致。
- 连接阶梯达到某档失败时记录失败原因，先定位再增加负载，不跳过失败直接宣布更高容量。

## 6. 每次运行需要保存的内容

建议路径：`docs/results/YYYY-MM-DD/<run-id>/`，至少包括：

- `environment.md`：日期、机器/OS、CPU/内存、JVM/GC/堆、框架/k6/Node 版本、网络路径、服务端与客户端是否同机。
- `config.json`：场景、连接数、房间分布、发送者数、目标/实际速率、消息字节数、队列/限流/线程参数、广播模式。
- `commands.md`：启动、采集、压测命令和步骤；不包含密钥或个人凭证。
- `summary.json`：客户端接收、重复/缺失/乱序、延迟分布、拒绝、丢弃、异常断连。
- `server-metrics.*`：代表性时序指标，覆盖预热、测量、排空和清理。
- `notes.md`：代码提交、工作区是否有未提交修改、异常、瓶颈证据和结论。

没有 Git 提交时可以临时使用源码哈希标识；正式对照应绑定清晰的代码版本和配置。大体积数据保存位置与哈希写入索引，保留足够复核的摘要和代表性原始证据。
